# 腾讯办公生态场景模拟测试设计

## 一、测试定位

本轮测试以 WorkBuddy 为核心对象，研究其进入腾讯办公生态后的能力适配与产品化路径。测试不验证 WorkBuddy 已经完成企业微信、腾讯文档、腾讯会议或腾讯表格的真实接口接入；没有企业微信账号、联系人和多人协作环境时，不能将模拟结果表述为真实集成效果。

本轮验证的是另一件更基础、也更可操作的事：当用户把腾讯办公生态中典型的项目文档、会议纪要、沟通记录、结构化业务资料和知识材料交给 WorkBuddy 时，WorkBuddy 能否完成跨材料理解、办公交付、证据复核、追加修改与成本可控的模型路由。

因此，正式名称统一使用“腾讯办公生态场景模拟测试”。

## 二、围绕腾讯生态的核心假设

### 假设 A：腾讯生态的价值在于办公信息流串联

腾讯办公场景的关键不是单一文档生成，而是把沟通、会议、文档与表格中分散的信息连接起来。WorkBuddy 应能将这些材料转为可执行、可审阅的单人办公交付物。

### 假设 B：WorkBuddy 更适合带人工复核闭环的办公执行

测试不要求 WorkBuddy 像成熟研究型 agent 一样一次成稿且高置信地完成所有深度研究。更关注其能否给出证据、暴露冲突和不确定项，并让用户快速完成最终确认。

### 假设 C：强模型应当用于关键节点，而不是默认全量开启

腾讯混元 HY3 作为免费基础模型，DeepSeek V4 Flash API 作为高级模型。比较两者时固定 Skill、提示词、材料和输出格式，不使用 Auto 模式，避免 MAX 自动开启造成模型、模式和成本混杂。

高级模型只有在明显降低事实错误、漏检、结构化失败或人工复核量时，才构成可被企业用户接受的付费价值。

## 四、HERB：综合办公交付任务包

### 4.1 选材原则

从 HERB 中选择同一产品或项目的关联材料，不运行全量语料。每个任务包应包含：

- 项目或内部文档；
- 至少一份会议转录或会议聊天；
- 至少两段与项目有关的消息记录；
- 可用于判断项目状态的结构化资料或客户资料；
- 存在版本变化、信息冲突或信息缺失的材料。

所有材料均为公开基准中的既有内容。为适配 WorkBuddy 的上传方式，可以保留原文并进行格式归档，但不得改写事实、补造角色或增加材料中不存在的业务信息。

### 4.2 主任务

给定同一项目的材料，要求 WorkBuddy 输出《项目状态报告》，固定包含：

1. 当前目标与项目状态；
2. 已确认的关键进展；
3. 风险、冲突信息与最新判断；
4. 待确认事项；
5. 下一步行动建议；
6. 每个关键结论的材料来源。

随后提供一条来自已有材料、且会改变部分结论的追加修改指令，要求 WorkBuddy 修订报告并简述修改原因。

### 4.3 客观评分

以 HERB 原始问题为锚点，将一个任务包对应的 6 至 10 个问题映射为报告中的必填事实字段。评分不以文风为主，而包括：

| 维度      | 分值  | 判断依据              |
| ------- | ---:| ----------------- |
| 关键事实正确性 | 35  | 与原始答案一致           |
| 证据定位与引用 | 20  | 使用正确材料，不引用无关或过期资料 |
| 冲突与时效处理 | 15  | 能识别冲突、最新版本与不确定项   |
| 办公交付完整性 | 15  | 六个固定模块完整、信息可扫描    |
| 修订响应    | 10  | 修改正确且不破坏未变事实      |
| 人工复核友好度 | 5   | 待确认项明确、无需在全文中反复检索 |

总分 100 分。对于原始基准标注为不可回答的问题，正确行为是明确说明材料不足；编造答案记为错误。

## 五、MuDABench：中文企业知识分析任务包

### 5.1 选材原则

使用 `complex.json`，冻结 6 个分层样本。每个样本仅上传其 metadata 指向的源 PDF，避免无关文档对模型造成不必要干扰。该数据集为中文 A 股正式材料，能够模拟企业知识库中的公告、报告、表格和多文档分析任务。

### 5.2 固定提示词

主实验要求生成 Markdown 文件，并在对话中简要说明已完成。请仅依据上传材料回答问题，并按以下结构输出：

1. 最终结论；
2. 支撑结论的关键事实与计算过程；
3. 来源文件及对应证据；
4. 不确定项或需要人工确认的事项。

若材料无法支持结论，必须明确说明“材料不足，无法确认”，不得基于常识补充。

### 5.3 评分

| 维度      | 分值  | 判断依据                        |
| ------- | ---:| --------------------------- |
| 最终结论    | 45  | 与 final_answer 的一致程度        |
| 支撑事实与推理 | 25  | 与 source_answer 的覆盖程度和逻辑正确性 |
| 证据可复核性  | 15  | 正确列出来源文件、事实位置或可定位描述         |
| 不确定性表达  | 10  | 不把推测写成事实，缺证时能拒答             |
| 输出结构    | 5   | 四段结构完整、便于人工审阅               |

总分 100 分。

## 六、HY3 与 DeepSeek V4 Flash 的对比规则

| 项目    | 固定规则                           |
| ----- | ------------------------------ |
| 模型    | 手动指定 HY3 与 DeepSeek V4 Flash   |
| Skill | 使用同一套 Skill；如需调整，两个模型同步调整并记录版本 |
| MAX   | 手动记录开关状态；主对比不得让其中一组自动开启        |
| 输入    | 同一任务包、同一文件、同一顺序、同一提示词          |
| 输出    | 相同的固定结构，禁止按模型能力临时降低要求          |
| 记录    | 质量分、耗时、积分或 API 成本、失败次数、人工复核问题数 |

DeepSeek V4 Flash 不具备视觉能力时，不将原生 PPT 版式、图像识别等项目纳入 HY3 对 DeepSeek 的主对比。主对比以可解析文本、结构化材料和可定位证据为主；视觉或版式能力可另列为 WorkBuddy 整体能力观察，不归因于模型推理能力。

## 七、腾讯生态优势如何在测试中被充分呈现

本轮不以“是否存在真实腾讯接口”取胜，而以腾讯办公用户最常见的工作对象与交付习惯作为测试约束：

1. 多来源材料：沟通、会议、文档、表格和知识资料共同构成任务上下文；
2. 中文业务语境：MuDABench 验证中文正式材料与定量分析；
3. 文档化交付：结果不是一句答案，而是可存入文档、可继续修改的项目报告和风险清单；
4. 人工复核：每个关键结论要求来源，冲突和材料不足需要显式暴露；
5. 模型梯度：用免费 HY3 覆盖高频基础任务，用 DeepSeek 处理真正需要更强推理的节点；
6. 可扩展链路：未来若取得腾讯文档、腾讯会议、企业微信的真实访问权限，可将同一任务包直接替换为真实导入、写回和通知流程，而无需改变评分逻辑。

## 八、本轮边界

- 不测试企业微信联系人、群聊、消息发送与审批流；
- 不宣称已经完成腾讯产品真实 API 或权限集成；
- 不将 DeckBench 作为必做项目；
- 不将模型分数直接等同于腾讯生态商业价值；
- 结论以 WorkBuddy 的办公 agent 定位为中心，ChatGPT Work 与 TRAE Work 如参与，仅作为参照组。

## 九、执行顺序

1. 下载并检查 HERB 与 MuDABench 的许可、文件格式和题目字段；
2. 各选取一个小规模试运行集，先验证 WorkBuddy 的文件上传、解析和输出稳定性；
3. 固化任务包、提示词和评分表后，分别运行 HY3 与 DeepSeek V4 Flash；
4. 记录质量、耗时、积分/API 成本和人工复核问题；
5. 再决定是否让 ChatGPT Work、TRAE Work 参与同一任务包的参照测试。
