# 腾讯生态测试优化方案 v2 —— 从「模型分级」到「生态证据链」

> 修缮对象:《腾讯办公生态场景模拟测试设计.md》(下称 v1)
> 修缮时间:2026-08-06
> 修缮理由:用户自检发现 v1 存在三个缺口——「没有真正使用腾讯生态」「生态价值无法考核」「测试退化为模型分级比较」。本文档给出三层证据链架构,补齐真实生态闭环与摩擦对比,让 04 模块真正回答主报告的 RQ4(腾讯生态价值)与 H4(生态假设)。

---

## 一、问题诊断:你的三个担忧都成立

### 缺口 1:模拟 ≠ 生态,全程零真实连接器交互

v1 已完成的 HERB 四组与待跑的 MuDABench,本质是「把腾讯场景形态的材料,以本地文件方式上传,再输出本地 Markdown」。全程没有发生任何一次:

- 在腾讯文档中创建、写回、再读回文档;
- 向乐享/ima 知识库写入并检索;
- 通过 QQ 邮箱/智能体邮箱分发交付物;
- 用腾讯系 PPT 技能生成交付物。

材料「像」腾讯场景,但腾讯产品一次都没有参与。「腾讯生态场景模拟测试」这个名字是诚实的,但也正暴露了问题:**它测的是材料消化能力,不是生态连接能力**——后者恰恰是主报告 RQ4 要回答的问题。

### 缺口 2:现有评分体系无法考核生态价值

v1 的评分维度(事实正确性、证据定位、冲突处理、交付完整性、修订响应、人工复核友好度)全部是**模型能力指标**。用这套表跑完,只能得出「哪个模型在这个材料流上表现好」,得不出「腾讯生态是否降低工作流摩擦、是否形成黏性」。

生态价值要考核的是另一组东西:能不能写回、写回后格式保不保真、能不能在文档里继续修订、能不能沉淀进知识库并被检索、相比传统工作流少切了几次软件、少做几个动作。

### 缺口 3:模型对比喧宾夺主,与既有测试重复

HERB 四组(HY3 / HY3+MAX / DS / DS+MAX)的结论「DS 满分、HY3 靠 MAX 补救」,与测试一《智谱专题研究》里 WorkBuddy 换模型复测的结论高度同构(见《本对话交接总结.md》第五节)。**04 模块如果以模型对比为主体,等于把测试一复测一遍**,而腾讯生态这个本轮主题反而缺席了。

> 结论:v1 不是设计错了,是**执行时丢掉了纲领文件里原本规划好的东西**。根目录《WorkBuddy专题研究设计.md》第 9.1 节「腾讯文档闭环(读/分析/写回/保格式/权限)」原本就是特色能力实验,但 v1 执行时用「模拟材料」替代了它。修缮方向是把它捡回来、做实。

## 二、优化总览:三层证据链

| 层 | 名称 | 内容 | 回答什么问题 | 是否已具备条件 |
|---|---|---|---|---|
| L1 | 能力层(模拟) | HERB 跨材料交付 + MuDABench 中文知识分析(HY3/DS 两组) | WorkBuddy 能否消化腾讯场景形态的材料并产出可复核交付物 | 已跑 HERB,补跑 MuDABench |
| L2 | **真实闭环层(新增)** | 腾讯文档写回/读回、乐享或 ima 知识库沉淀与检索、腾讯系 PPT 生成、QQ 邮箱分发 | 生态连接是宣传还是真的能读写、能减少步骤(H4 直接验证) | **已具备:tencent-docs、lexiang、ima、qq-mail、agent-mail 连接器均已连接;tencent-pptx、tencent-local-office-edit 技能可用** |
| L3 | **摩擦对比层(新增)** | 同一交付任务,「WorkBuddy+生态闭环」 vs 「浏览器+本地Office+邮箱」传统人工基线 | 生态闭环相对传统工作流实际减少多少摩擦(可量化 ROI) | 具备,需做一组基线对照 |

三层递进关系:

```text
L1 证明「材料进来能消化」   ← 已有能力,客观可评分
        ↓
L2 证明「成果能写回生态、能被检索、能分发」 ← 本轮新增核心,WorkBuddy 差异化证据
        ↓
L3 证明「相比传统工作流,整体摩擦确实下降」  ← 商业付费论证(RQ5)的前置证据
```

**分工原则(解决「退化为模型比较」):**
- L1 的模型对比(HY3 vs DS)只回答一个问题:**企业版模型路由怎么选**(低成本覆盖高频、强模型留给关键节点),它从「主角」降级为「配套」;
- L2/L3 才是 04 模块的主角,产出的是**生态闭环成功率与摩擦减少量**,而非模型分数。

## 四、L2 真实闭环层(本轮核心新增)

### 4.0 执行方式与通用记录项

- 用户在 WorkBuddy 对话中下达固定指令(见各任务),WorkBuddy 执行,用户按既有惯例手动记录:总耗时、积分、人工介入次数、失败/重试。
- 每个任务输出一张「闭环执行记录表」,保存到 `04_腾讯生态\操作记录\生态闭环记录\`。
- 通用记录项:任务编号、目标应用、连接器状态、动作序列(每步)、每步是否人工介入、失败点、重试次数、耗时、积分。

### 4.1 R1 腾讯文档写回与增量修订闭环

**目的**:验证「腾讯文档 = 交付出口 + 持续维护载体」,直接对应纲领 9.1「腾讯文档闭环」。

**步骤**:
1. 将 HERB-01 报告(Markdown)→ 在腾讯文档创建在线文档并写入;
2. 人工在腾讯文档中(或在对话中)追加 HERB-02 的新材料 → 让 WorkBuddy 读取该在线文档 → 输出修订版报告 → 写回同一文档;
3. 从文档读回最终内容,与本地修订版比对。

**通过判据**:
- 文档创建成功、可打开、可分享;
- 写回内容完整,标题层级/表格/加粗等基础格式保持;
- 二次修订正确进入文档,且未破坏未变内容(与本地基线逐段比对);
- 全程步骤数与人工介入次数被记录。

### 4.2 R2 知识库沉淀与检索闭环(乐享 或 ima,二选一优先乐享)

**目的**:验证「知识库 = 长期记忆载体」,对应纲领 6.1 企业能力与 RQ4 的「数据读取或写回」。

**步骤**:
1. 在乐享知识库建一个测试空间/文档,把 MuDABench 的 6 份源 PDF 或 HERB 材料包上传入库;
2. 让 WorkBuddy 基于知识库内容回答一个固定问题(引用库内文档);
3. 记录:入库是否成功、检索是否命中、引用是否指向库内正确文档、未入库内容是否被正确拒答。

**通过判据**:入库成功率 100%(允许人工修正路径问题,但必须记录)、检索命中、引用可定位、无库内容不编造。

### 4.3 R3 交付分发闭环(腾讯系 PPT + QQ 邮箱)

**目的**:验证「生成 → 分发」一步到位,对应纲领「内容交付 + 邮件」场景与测试一交付物形态。

**步骤**:
1. 基于 HERB-01 报告,用腾讯系 PPT 技能生成 5 页《ProposalForce 项目简报》;
2. 将 PPT 与报告打包,通过 QQ 邮箱(或智能体邮箱)发送到用户指定邮箱;
3. 记录:PPT 生成成功率、文件可打开性、邮件发送状态。

**通过判据**:PPT 生成成功且可打开、内容与报告一致、邮件发送成功。

### 4.4 R4 本地 Office 编辑(可选,有余力再做)

用 `tencent-local-office-edit` 对本地 docx/xlsx 做一处真实修改(如更新一个表格数字并保存),验证「本地 Office 所见即所得编辑」这一 WorkBuddy 特色能力。

## 五、L3 摩擦对比层(新增)

### 5.1 对照设计

选一个 L2 已跑过的同构任务(建议 R1 的「报告写回并分发」),用两条路径各做一遍:

| 维度 | A 路径:WorkBuddy + 腾讯生态闭环 | B 路径:传统人工工作流 |
|---|---|---|
| 工具链 | WorkBuddy + 腾讯文档 + QQ 邮箱 | 浏览器下载 → Word/WPS 排版 → 邮箱附件发送 |
| 记录项 | 步骤数、软件切换次数、人工动作数、总耗时 | 同左 |
| 执行方式 | 对话下达,WorkBuddy 执行 | 用户手工完成(或按经验精确估算并标注) |

### 5.2 摩擦指标定义

- **操作步骤数**:从任务下达到处分完成,记录的最小动作单元数(点一次按钮/发一条指令/打开一个文件都算一步);
- **软件切换次数**:不同应用之间切换的次数;
- **人工动作数**:需要人工亲自完成的动作(非审核确认);
- **总耗时**;每步失败/重试数。

### 5.3 预期产出

一张对比表 + 一段结论,直接支撑主报告 13.3「腾讯生态协同」的「减少软件切换、减少人工步骤」论证。**这是 v1 完全没有、而 RQ4 最需要的证据。**

## 六、生态专属考核指标体系(新增评分表)

每项有客观判据,不再只靠人工读报告打分:

| 指标 | 判据 | 数据来源 | 说明 |
|---|---|---|---|
| 连接器接入成功率 | 授权/连接是否成功,失败是否可修复 | 连接器状态 | 反映产品当前生态成熟度 |
| 写回成功率 | R1 文档创建/写入是否成功 | R1 记录 | 失败即生态不可用 |
| 往返数据保真度 | 写回→读回后内容与本地基线的一致率(字段级/段级) | R1 逐段比对 | 定量,按段落数计算 |
| 格式保持率 | 标题、表格、列表、加粗在文档中是否保持 | R1 人工核验 | 定性转定量(保持/丢失/乱码) |
| 增量修订闭环 | 二次修订是否只改应改处 | R1 比对 | 对应 H2 连续性假设 |
| 知识库沉淀与检索 | 入库成功率、检索命中率、引用可定位性 | R2 记录 | 对应企业能力 |
| 摩擦减少量 | Δ步骤数、Δ软件切换、Δ人工动作、Δ耗时 | L3 对比表 | 生态价值核心量化指标 |
| 分发成功率 | PPT 可打开、邮件送达 | R3 记录 | 交付闭环完整性 |
| 成本 | 积分/API 消耗 | 用户记录 | 与既有口径一致 |
| 失败与边界 | 失败点、重试、权限/格式问题 | 各任务记录 | 写入报告「失败案例」节 |

权重建议:L1 质量分与 L2/L3 生态分**分开计、不合并**,报告中并列展示。因为两者回答的问题不同,强行合成一个总分反而说不清。

## 八、连接深度分级表:诚实边界的实证填充

主报告 6.2 节有一张「连接层级表(登录/入口/数据/执行/商业)」。04 模块结束后,把 L2 实测结果填进去,**这张表就从「产品宣传整理」变成「实证结果」**:

| 层级 | 含义 | 04 实测状态 |
|---|---|---|
| 登录层 | 腾讯账号登录 | 已实测(WorkBuddy 登录) |
| 入口层 | 微信/企微/QQ 下发任务 | **未实测**(未连接企微,如实标注为待验证) |
| 数据层 | 读取腾讯文档/知识库内容 | **已实测**(R1 读回、R2 知识库检索) |
| 执行层 | 在生态应用中写入、修改 | **部分实测**(R1 文档写回、R2 入库成功;企微发送/会议操作未实测) |
| 商业层 | 带动腾讯云/模型/企业软件付费 | 分析性结论,由 05 商业化模块承接 |

**报告写法原则**(延续项目一贯的严谨):「L2 只证明文档/知识库/邮箱这三条链路真实可用;入口层(企微远程)与会议链路因账号条件未实测,属待验证项」——**不实测就不声称**,这本身就是研究可信度的体现,也是面试加分点。

## 十一、风险与注意事项

1. 连接器状态会变:执行 L2 前先确认 tencent-docs/lexiang/ima/qq-mail 处于已连接状态;某连接器临时不可用则改期,不硬跑;
2. 格式保真需人工核验:机器比对只查内容一致性,格式(表格/标题)需用户目视确认,记录「保持/丢失/乱码」;
3. L2 不参与三家竞品总分:只有 WorkBuddy 有这些连接器,竞品对照不可行,定位为「WorkBuddy 差异化验证」(与纲领第九章一致);如需对照,可在报告中讨论 ChatGPT 用 Google Docs/Notion 的替代路径,但归入讨论而非评分;
4. 成本口径继续沿用「积分波动不作模型切换证据」原则;
5. 本文档不改动 v1 已冻结的 L1 规则与评分锚点,只做定位调整与新增层。
