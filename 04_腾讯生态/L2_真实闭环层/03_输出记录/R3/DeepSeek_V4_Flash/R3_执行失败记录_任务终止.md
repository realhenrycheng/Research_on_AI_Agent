## 二、遇到的问题与调整思路

### 问题 1:tencent-pptx skill 本地运行时无法安装
- **现象**:skill 依赖 slidep@5.4.1(随插件 vendor 分发),需 npm 安装。npm 全局安装连续失败:`[safe-delete] 操作失败`、ERESOLVE peer 冲突;手动解压后 canvas 等原生依赖缺失,引擎无法启动。
- **调整思路 1**:清理 npm 缓存重试、`--no-safe-delete`、`--legacy-peer-deps`、手动放置包——均未解决,且该过程耗时约 10 分钟。
- **调整思路 2(采纳)**:放弃本地引擎,改用**已连接的 kdocs 连接器 aippt 能力**生成 PPT(零安装),此路成功。
- **教训**:遇到「skill 运行时依赖装不上」时应第一时间切换到已连接连接器的等价能力,而不是反复尝试安装。

### 问题 2:QQ 邮箱附件传参通道限制
- **现象**:qq-mail 连接器 SendMessage 附件仅支持 base64 内联(attachments.content)或 file_refs(需 CLI 上传,本机无本地 MCP 客户端,mcporter 不可用)。PPT 初始 1.6MB,base64 约 220 万字符,远超工具参数可承载范围。
- **调整思路 1**:压缩 PPT 内图片(4001×2250→800px→500px,PNG→JPEG),文件降到 0.32MB。
- **调整思路 2**:生成 python-pptx 精简版(36KB),base64 48K 字符。
- **调整思路 3**:再精简至 18KB,两个附件 base64 合计约 48K 字符后重试。
- **结果**:即便 48K 字符,带附件调用 SendMessage 仍无返回(疑似工具调用参数过大/超时),始终未突破该通道瓶颈。
- **教训**:① 手动在对话内拼接 base64 从根上不可行(Read 工具对超长单行截断,无法完整转述);② 应在第一次遇到「base64 过大」时就明确判定该通道不可用,转而询问用户是否接受替代方案(如:先上传微云再发链接、改用 agent-mail 通道、或拆分附件),而不是反复压缩重试。③ 对 MCP 工具参数体量边界缺乏事前评估,导致多次空转。

### 问题 3:确认令牌过期与调用无返回
- **现象**:QQ 邮箱两阶段确认令牌 5 分钟过期;多次尝试期间令牌过期,重试需重新获取;带附件调用偶发无任何返回(疑似超时)。
- **教训**:交互链路一旦拖长,确认令牌过期会让每次重试成本叠加,应先解决参数体量问题再走确认流程。
